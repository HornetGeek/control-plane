# Research: Control Plane MVP

**Feature**: Control Plane MVP
**Date**: 2026-02-09
**Status**: COMPLETE

## Overview

This document consolidates research findings for the Control Plane MVP implementation. All technical decisions are derived from the Control Plane Constitution (v1.0.0).

---

## Technology Stack Decisions

### Language & Framework

**Decision**: Python 3.11+ with FastAPI

**Rationale**:
- Python 3.11+ provides significant performance improvements and better async support
- FastAPI is a modern, fast (ASGI) web framework for building APIs
- Native OpenAPI 3.0 schema generation
- Built-in Pydantic v2 integration for request/response validation
- Excellent async support for database operations

**Alternatives Considered**:
- Node.js/Express: Rejected due to team's Python expertise and existing ecosystem
- Go/Fiber: Rejected due to faster development time with Python
- Django Ninja: Rejected due to less maturity than FastAPI

### Data Layer

**Decision**: PostgreSQL with SQLAlchemy 2.0 (async)

**Rationale**:
- PostgreSQL is the constitution-mandated database choice
- SQLAlchemy 2.0 provides a mature, well-documented ORM with async support
- Alembic for database migrations (standard tool for SQLAlchemy)
- AsyncPG driver for high-performance async database operations

**Alternatives Considered**:
- MongoDB: Rejected per constitution (PostgreSQL required)
- Tortoise ORM: Rejected due to less maturity than SQLAlchemy
- SQLModel: Rejected due to beta status and limited feature set

### Authentication

**Decision**: OpenID Connect with Zitadel

**Rationale**:
- Per constitution requirement: OIDC with Zitadel (auth.craft-crew.com)
- Authorization code flow for secure token exchange
- JWKS endpoint for signature verification
- Required claims: `sub` (user ID), `org_id` (organization association)

**Alternatives Considered**:
- Direct OAuth2: Rejected due to constitution requirement
- Custom JWT handling: Rejected due to security concerns

### Testing

**Decision**: pytest with async support

**Rationale**:
- pytest is the de facto standard for Python testing
- pytest-asyncio for async test support
- httpx for async HTTP test client
- pytest-cov for coverage reporting

**Alternatives Considered**:
- unittest: Rejected due to less feature-rich than pytest
- nose2: Rejected due to lack of maintenance

## Architecture Patterns

### API-First Design

**Pattern**: REST API with OpenAPI 3.0 specification

**Rationale**:
- All functionality exposed via REST endpoints
- No web UI in this service (per constitution)
- OpenAPI schema auto-generated by FastAPI
- Enables multiple client types (web, mobile, other services)

### Multi-Tenancy Model

**Pattern**: Hierarchical tenancy with strict isolation

**Structure**:
```
Organization (1) ──┬── Tenant (N)
                    └── User (N) ── Membership (M) ── Tenant (N)
```

**Rules**:
- User belongs to exactly one Organization
- Tenant belongs to exactly one Organization
- User can have multiple Memberships (different Tenants) within same Organization
- Cross-organization access is FORBIDDEN

### Authorization Model

**Pattern**: Coarse-grained role-based access control

**Roles**:
- `org_admin`: Can manage all tenants within their organization
- `tenant_admin`: Can manage a specific tenant only
- `tenant_member`: Read/launch access for that tenant

**Rationale**:
- Simple, predictable authorization for MVP
- No custom roles or complex permissions
- Role stored on Membership entity

### Idempotency Strategy

**Pattern**: Database unique constraints

**Implementation**:
- `Membership`: Unique constraint on (tenant_id, user_id)
- `Subscription`: Unique constraint on (tenant_id, app_key)

**Rationale**:
- Database-enforced idempotency
- Simplifies error handling for clients
- Supports retry logic in distributed systems

## Security Considerations

### Token Validation Flow

```
Request → Extract Bearer Token → Verify Signature via JWKS
→ Validate Claims (iss, aud, exp) → Extract sub and org_id
→ Lookup User → Attach to Request State
```

### Authorization Flow

```
Authenticated Request → Check Organization Boundary
→ Check Tenant Membership → Check Subscription (if applicable)
→ Apply Role Permissions → Allow/Deny
```

### Correlation ID Strategy

- Accept `X-Request-ID` header from client
- Generate UUID v4 if not provided
- Return in all response headers
- Include in all log entries

## Performance Considerations

### Database Optimization

- Connection pooling via SQLAlchemy (async)
- Indexes on foreign keys and frequently queried columns
- Unique constraints for idempotency also serve as indexes

### Caching Strategy

- JWKS keys cached (TTL: 5 minutes) to reduce OIDC provider calls
- Application catalog cached in memory (rarely changes)
- No user/tenant caching (data freshness required)

### Async Operations

- All I/O operations are async:
  - Database queries (SQLAlchemy 2.0 + AsyncPG)
  - HTTP requests (httpx async client)
  - OIDC token validation (async JWKS fetch)

## API Design Patterns

### Endpoint Conventions

- All endpoints under `/v1/` prefix
- Resource names are plural (`/tenants`, `/memberships`)
- Nested resources use path parameters (`/tenants/{id}/members`)

### Error Response Format

```json
{
  "code": "ERROR_CODE",
  "message": "Human-readable description",
  "details": {},
  "request_id": "uuid"
}
```

### Pagination

For list endpoints:
- Query params: `limit` (default: 50, max: 1000), `offset` (default: 0)
- Response: `{"total": N, "limit": 50, "offset": 0, "items": [...]}`
